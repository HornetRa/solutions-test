# solutions-test

Digital business card API built with NestJS, GraphQL, Prisma and PostgreSQL.

## Запуск через Docker (проще всего)

```bash
docker compose up -d
```

Поднимет базу и приложение, сам накатит схему и засеет данные.

- GraphQL sandbox: http://localhost:3000/graphql
- Health check: http://localhost:3000/health

Остановить:

```bash
docker compose down
```

## Локальный запуск

1. Установить зависимости:

```bash
npm install
```

2. Скопировать `.env.example` в `.env` и при необходимости поправить:

```bash
cp .env.example .env
```

3. Поднять базу (только Postgres, без приложения):

```bash
docker compose up -d db
```

4. Накатить схему и засеять данные:

```bash
npm run db:push
npm run db:seed
```

5. Запустить приложение:

```bash
npm run start:dev
```

## Тесты

Юнит-тесты:

```bash
npm run test
```

E2E-тесты (нужна отдельная тестовая база):

```bash
docker compose up -d db-test
npm run test:e2e
```

Строка подключения для e2e лежит в `.env.test` (уже в репозитории, отдельно от `.env`) и указывает на `db-test` (порт 5433), поэтому реальную dev-базу тесты не трогают. Перед прогоном `test:e2e` скрипт `pretest:e2e` сам накатывает схему в тестовую базу (`prisma db push`), вручную ничего готовить не нужно, кроме поднятого контейнера `db-test`.

## Линт и форматирование

```bash
npm run lint
npm run format
```


# Архитектурные решения

## Стек

NestJS + GraphQL (code-first) + Prisma + PostgreSQL, всё поднимается через Docker.

## Prisma 6.19.3, а не последняя версия

На момент разработки `latest` у `prisma` указывал на `8.0.0-rc.13`: нестабильный release candidate. Prisma 7 к тому же убирает `url` из блока `datasource` в schema-файле (нужны driver adapters / `prisma.config.ts`). Для этой задачи это лишняя сложность, поэтому зафиксирована последняя стабильная версия 6.19.3, с классическим `datasource db { url = env("DATABASE_URL") }`.

## GraphQL: code-first, а не schema-first

Схема (`src/schema.gql`) генерируется автоматически из декораторов (`@ObjectType`, `@Field`, `@Resolver`) через `autoSchemaFile`не пишется руками. Плюс, типы TypeScript и GraphQL-схема гарантированно не расходятся, минус меньше контроля над итоговым SDL (`sortSchema: true`, порядок полей был стабильным и предсказуемым в диффах).

`introspection: true` выставлена явно, по умолчанию в `NODE_ENV=production` она отключается, а для тестового важнее, чтобы Apollo Sandbox работал и на проде, а не только локально.

## Валидация окружения

`ConfigModule` с Joi-схемой (`env.validation.ts`) проверяет `DATABASE_URL`/`PORT`/`NODE_ENV` при старте. Если переменная отсутствует или некорректна, приложение падает сразу при запуске с понятной ошибкой, а не где-то в рантайме при первом обращении к базе.

## Health-check не заглушка

`/health` реально делает `SELECT 1` через Prisma (`prisma.$queryRaw`), а не просто отвечает `200 OK`. Так health-check в Docker Compose и на хостинге действительно проверяет, что база доступна, а не только жив ли процесс Node.

## Docker: self-initializing контейнер

`docker-entrypoint.sh` при каждом старте сам прогоняет `prisma db push` и сид базы перед запуском сервера. Это осознанный выбор для демо-проекта: разворачивается одной командой (`docker compose up`), без ручных миграций. В проде с реальными данными так делать не стоит, там нужны версионируемые `prisma migrate` вместо `db push`, чтобы иметь историю схемы и возможность отката.

## Тестовая изоляция

Для e2e есть отдельный сервис `db-test` в `docker-compose.yml` (свой порт 5433, без volume) вместо общей с dev базы. Тесты не зависят от состояния локальной базы разработки и не портят её данные.

## CI: три независимых джоба

`lint-and-unit`, `e2e` с отдельным Postgres-сервисом в GitHub Actions и `docker-build` разнесены специально, чтобы падение линта не блокировало проверку сборки образа, и наоборот, и чтобы в логах сразу было видно, что именно не прошло.

## Авторизация

Цифровая визитка одного человека, а не мультипользовательская система. Городить полноценный auth (регистрация, хеширование паролей, JWT с refresh-токенами, таблица users) оверинжиниринг: пользователь один, и он же администратор.

Если нужно защитить мутации от анонимной записи, разумный вариант, простой guard, сверяющий заголовок `Authorization: Bearer <token>` со значением `ADMIN_TOKEN` из `.env`. Чтение (`Query`) остаётся полностью публичным так как визитка, её и задумано показывать всем. Полноценный `Passport` или `JWT` имел бы смысл только при появлении второго пользователя или ролей, сейчас такой необходимости нет.
